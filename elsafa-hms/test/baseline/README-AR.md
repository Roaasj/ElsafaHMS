# الخط الأساسي المحاسبي (Baseline)

مرجع ثابت لأرقام النظام الحالي (v0.16) قبل أي تغيير في طبقة المبالغ. **أي اختلاف غير مفسَّر = فشل المرحلة.**

## الملفات
- `scenario.js`: سيناريو ثابت (29 خطوة) على SQLite في الذاكرة + بيانات `seed-demo`. مستقل عن كود المبالغ (مفيش import لـ `cents/pounds`).
- `baseline.golden.json`: النتائج المرجعية المسجَّلة (متحكَّم فيها، مش بتتعدل بالإيد).
- `record.js`: بيسجّل الملف المرجعي (مرتين للتأكد من الثبات، ومش بيكتب فوق موجود إلا بـ `--force`).
- `baseline.test.js`: بيشغّل السيناريو ويقارن بالمرجعي، ويطلع مسار كل اختلاف.

## إعادة التشغيل
```
node --test test/baseline/baseline.test.js     # مقارنة (بعد كل مرحلة)
node test/baseline/record.js --force           # تسجيل خط جديد: بس بموافقة صريحة بعد تفسير الاختلاف
```
النتيجة لا تعتمد على اليوم ولا الساعة. السيناريو بيرفض الإكمال لو اتعدّى منتصف الليل (القاهرة) أثناء التشغيل.

## اللي بيتسجّل
1. **كل صف مالي** (109 صف) في: الإيصالات وبنودها، بنود الزيارات والدخول، الدخول، نسب الأطباء، دفتر الجهات، أذونات الدفع، الموافقات، المطالبات وبنودها وسدادها، مستحقات الأطباء، السندات.
2. **عدد الصفوف والمجاميع** لكل جدول فيه عمود رقمي (39 جدول)، بوحدة 1e-4 كأعداد صحيحة (من غير فاصلة عائمة).
3. **ملخص لكل نوع عملية** (`byType`): الإيصالات حسب النوع والإشارة، الأذونات، البنود حسب القسم والحالة، نسب الأطباء (موجب/سالب)، دفتر الجهات (تحميل/عكس)، المطالبات، المستحقات والضريبة، السندات، فواتير الموردين، المصروفات، حركات المخزن.
4. **التقارير:** تقرير الخزينة (بدون أي حقل وقت) وكشف حساب كل جهة تعاقد.
5. **جدول التقريب** (`rounding`): السلوك الحالي موثّق بأمثلة (انظر تحت).
6. **الصيغ المكتوبة** (`words`): تفقيط المبلغ بالجنيه/قرش.
7. **العيوب المعروفة** (`known`): متثبّتة زي ما هي. أي إصلاح لها بيظهر كاختلاف ويحتاج موافقة.

## سلوك التقريب الحالي (قبل أي تغيير)
- كل الحسابات بالقروش كأعداد صحيحة وبـ`Math.round` (نصف لفوق، يعني 0.5→1، 1.5→2، 2.5→3).
- **السالب:** `Math.round(-2.5) = -2` و`Math.round(-0.5) = -0` (يقرّب ناحية +∞ مش بعيد عن الصفر). ده بيأثر على المرتجعات السالبة وده السلوك الحالي، وبيتحفظ.
- التقريب **لكل وحدة/بند** (مثلًا خصم 12.5% على 33.33 يطلع 29.16 للوحدة، فـ×3 = 87.48 مش 87.49).
- نسبة الدكتور والتغطية: تقريب على الإجمالي (`round(base × pct / 100)`).
- المرتجع الجزئي: `round(المدفوع × العدد ÷ الإجمالي)`.
- ضريبة مستحقات الأطباء: `round(الإجمالي × النسبة)` لكل دكتور.

## الفرق بين نوعين من اختبار العملات (مهم)
- **طبقة الحساب والعرض (R1a):** بتتختبر على SQLite بعملات 0 و2 و3 خانات. دي بتثبت إن الحساب والتقريب والتنسيق والطباعة سليمين.
- **التخزين الفعلي في SQL Server (R1c):** عمود `DECIMAL(12,2)` الحالي **مش بيخزن 3 خانات**، فاختبار ده فعليًا مستحيل قبل توسيع الأعمدة. وSQLite مش بديل (بيخزن أرقام عشرية عائمة). فاختبار 3 خانات على SQLite **لا يثبت** سلامة التخزين على SQL Server. التثبت الحقيقي بعد R1c على نسخة SQL Server حقيقية.

## حدود الخط الأساسي (صراحة)
- ده خط SQLite. مجاميع SQL Server هتتسجل لما تجرّب عندك (سكربت التحقق هيتجهّز في R1c).
- مفيش ضريبة قيمة مضافة على فواتير المرضى في النظام الحالي. الضريبة الوحيدة هي ضريبة مستحقات الأطباء (`doctorTaxPct`).
- اتغطّى في الخط B (تحت): المشتريات والتحويلات والجرد والهالك والأقساط وسداد السندات.
- لسه ما اتغطّاش: أرصدة مخزن بعد بيع/مرتجع على تشغيلات متعددة التكلفة، وتقارير الاستهلاك والراكد، وتصدير Excel.

## الخط B: المخازن والمشتريات والأقساط والسندات
ملفات: `scenarioB.js` · `recordB.js` · `baselineB.golden.json` · `baselineB.test.js`. قاعدة مستقلة في الذاكرة، والخط الأصلي ما بيتأثرش.
```
node --test test/baseline/baselineB.test.js    # 13 اختبار: مقارنة + نتائج متوقعة يدويًا + قيود سلامة
node test/baseline/recordB.js --force          # تسجيل جديد بموافقة صريحة
```
- **اللي بيتسجّل:** كل صف في المشتريات وبنودها والتشغيلات والحركات والتحويلات والإعدام والجرد والالتزامات والأقساط والإذونات وفواتير ودفعات الموردين، بالأعداد والمجاميع (1e-4)، وقيمة المخزون لكل مخزن بوحدة 1e-8، وتقرير قيمة المخزون وتقرير الخزينة.
- **نتائج متوقعة محسوبة يدويًا** (من غير كود المنتج): إجماليات المشتريات، تكلفة الوحدة الأساسية بـ4 خانات، تقسيم الأقساط، إذونات الخزينة، الإعدام، وحالات الرفض.
- **قيود سلامة:** رصيد كل تشغيلة = مجموع حركاتها، وحركات التحويل بتحافظ على الكمية.
- **ملاحظات مثبّتة:** استلام 12.5 × 1.15 بيطلع 14.37 مش 14.38 (فاصلة عائمة)، فإجمالي الاستلام 772.68. وتكلفة الوحدة الأساسية بتتخزن بـ4 خانات (100÷14 = 7.1429). وفي مشغّل SQL Server الأرقام الكسرية بتتربط (12,2) فالتكلفة دي ممكن تتقرّب هناك بس (معروف، مسجّل في `known`).

## الخط C: تشغيلات متعددة التكلفة، سالب، تقارير، إكسل
ملفات: `scenarioC.js` · `recordC.js` · `baselineC.golden.json` · `baselineC.test.js`. قاعدة مستقلة في الذاكرة.
```
node --test test/baseline/baselineC.test.js    # 19 اختبار

```
- **اللي بيتغطّى:** بيع من 3 تشغيلات بتكاليف مختلفة (FIFO بالأقرب انتهاءً) ومرتجع جزئي بيرجّع «آخر اللي اتصرف الأول»، بيع علبة ثم شرائط، تعديل وحذف بند غير مدفوع، إلغاء إيصال بيع، بيع على رصيد سالب (بصلاحية، ورفضه بدونها) وتسديد السالب بالاستلام، تحويل على تشغيلتين، إعدام وجرد، وبيع من الطوارئ.
- **نقاط فحص (checkpoints):** أرصدة كل تشغيلة بعد المبيعات وبعد السالب وبعد التحويل وبعد الإعدام، مقارنة بحساب يدوي مستقل (مكتوب في الاختبار).

- **التواريخ والأوقات** بتتحوّل لعلامة ثابتة (`<D>` و`<T>`) علشان النتيجة ما تتغيّرش بتغيّر اليوم. «سفر في الزمن» بيتم على القاعدة المؤقتة بـUPDATE مباشر (200 يوم للراكد، وتشغيلة منتهية).
