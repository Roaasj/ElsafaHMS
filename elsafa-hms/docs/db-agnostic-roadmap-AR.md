# استقلال قاعدة البيانات وإضافة PostgreSQL إلى الخارطة

**الحالة:** قرار معماري معتمد، التنفيذ مؤجَّل. ممنوع أي شغل PostgreSQL قبل استقرار SQL Server وإنهاء R1a (وR1c).
**الهدف:** تشغيل المنشأة على المحرك المناسب لها (SQL Server / PostgreSQL، وSQLite للتجربة والاختبار فقط) من غير إعادة تطوير وظائف البرنامج.

## 1) الوضع الحالي (قياس فعلي على الكود، قراءة فقط)
| البند | النتيجة |
|---|---|
| دوال خاصة بـSQL Server داخل `src/` خارج `src/db/` (GETDATE, DATEADD/DATEDIFF, ISNULL, CONVERT/CAST AS VARCHAR, OUTPUT INSERTED, IDENTITY, FORMAT, STRING_AGG, OFFSET/FETCH) | **صفر** |
| مراجع لنوع المحرك خارج طبقة القاعدة | سطران فقط في `server.js` (رسالة التشغيل ومسار ملف SQLite) |
| `db.top(sql, n)` | 38 استخدام، موحّدة وجاهزة لإضافة LIMIT |
| `insert()` | بترجّع `Id` عبر `OUTPUT INSERTED.Id`؛ في PostgreSQL = `RETURNING id` (مكانها داخل المحوّل) |
| عدّادات الترقيم | `Counters` + `t.nextNumber(name)` داخل المحوّل (جيدة؛ مفيش sequences في الكود) |
| الاستعلامات | SQL مشترك بعلامة `?`، والمحوّل يحوّلها (`@p0` لـSQL Server، و`$1` للـPostgreSQL) |

**نقاط الخطر الحقيقية (مش اللي في الكود، اللي حواليه):**
1. `db/schema.sqlite.sql` **متولّد بالترجمة** من DDL الخاص بـSQL Server (`scripts/gen-sqlite-schema.py`). النهج ده لا يتكرر مع PostgreSQL: الترجمة الآلية بتخفي فروقًا (الأنواع، `BIT`، `NVARCHAR`، الـcollation).
2. ملفات الهجرات `db/mssql/001..013_*.sql` مكتوبة بـT-SQL (ALTER/GO/CONSTRAINT)، ومفيش فولدر لمحرك تاني.
3. 17 موضع تجميع نصوص (`||` / `+`) و9 مواضع بحث نصي (LIKE/SUBSTR/LEN) داخل `routes/`: الأماكن الأولى للاختلاف (التجميع، حساسية الحروف، الـcollation العربي).
4. اختبارات SQLite = غير كافية كدليل توافق (القيم العشرية، الترتيب، التواريخ، العزل).

## 2) المبادئ المعمارية (ملزمة من الآن لأي كود جديد)
1. **الفصل:** منطق البرنامج (`routes/`, `lib/`) يتعامل مع `db` فقط، ولا يعرف المحرك. المحرك يُحدَّد بإعداد واحد (`DB_DRIVER`).
2. **العزل:** كل ما هو خاص بمحرك يعيش تحت `src/db/<engine>/` (محوّل + تهجير القيم + أخطاء المحرك) ولا يتسرب خارجه.
3. **طبقة توافق قبل أي SQL خاص:** لو احتجنا دالة مختلفة بين المحركات (تاريخ، تجميع نص، LIMIT، upsert، تجميع شرطي)، تتعمل لها دالة في `db` (مثل `db.top`) بتُرجع الشكل الصح لكل محرك، ولا تُكتب T-SQL مباشرة في ملف وظيفة.
4. **واجهة موحدة وضيقة:** `query / one / insert / run / tx / top / nextNumber` + (مستقبلًا) `now()`, `concat()`, `dateAdd()` عند الحاجة فقط. أي إضافة للواجهة تتوثق وتتنفذ في كل المحركات.
5. **الاختلافات اللي لازم تتصمم لها:**
   - **الأرقام العشرية:** `dec.money/cost/pct/qty` (Step 1) هي العقد. PostgreSQL فيه `NUMERIC(p,s)` ومحرّكه بيرجّع النص (string) افتراضيًا: لازم المحوّل يحوّله لرقم بنفس شكل `mssql`.
   - **التواريخ:** التخزين UTC و`Date`/ISO في التطبيق؛ ممنوع الاعتماد على التحويل الضمني أو توقيت السيرفر. التقسيم لأيام (اليوم/الشهر) يتم بمنطقة المنشأة في طبقة واحدة.
   - **الترقيم:** `Counters` داخل المعاملة (مستقل عن IDENTITY/SERIAL). `insert()` يرجّع الـId بغض النظر عن المحرك.
   - **المعاملات:** العزل `READ COMMITTED` في الاتنين، لكن السلوك مختلف (SQL Server = قفل، PostgreSQL = MVCC). أي كود بيقرأ ثم يكتب (رصيد مخزون، عدّاد، قسط) لازم يتختبر تحت تزامن على كل محرك، مش يُفترض.
   - **النص:** الـcollation العربي وحساسية الحروف والمسافات في البحث؛ البحث بطبقة موحّدة.
   - **المنطقي (BIT/BOOLEAN) والـNULL والـ`''`:** يتم عبر `toBool` والمحوّل.
6. **الهجرات لكل محرك مستقلة:** `db/mssql/` و`db/postgres/` (وSQLite يتولّد أو يُكتب يدويًا بنفس الأرقام). رقم النسخة (`LATEST`) واحد لكل المحركات ومعنى كل نسخة واحد، لكن نص التنفيذ مستقل. جدول `SchemaVersion` موحّد. اختبار يتأكد إن عدد وأسماء الجداول والأعمدة والأنواع المنطقية متطابقة بين المحركات (schema parity).
7. **نجاح SQLite لا يعني شيئًا للمحركات الأخرى:** SQLite للتجربة السريعة فقط. لا تُعتبر ميزة جاهزة إلا بعد نجاحها على SQL Server (ثم PostgreSQL عند وجوده). كل مرحلة بتتقفل بتشغيل Baselines A/B/C على المحرك الحقيقي.

## 3) ما سيُضاف داخل R1a بدون أي مخاطرة (مقترح، مش متنفذ)
- **حارس اختبار** (ملف اختبار جديد فقط، مفيش تغيير في المنتج): يفشل لو ظهرت دالة/صيغة خاصة بمحرك داخل `src/` خارج `src/db/`. مع قائمة استثناءات صفرية حاليًا (الوضع الحالي نظيف). يدخل ضمن Step 6 (guard tests).
- توثيق قائمة "الواجهة الرسمية للقاعدة" في README.

## 4) الخارطة
`R1a` (SQL Server مستقر) ← `R1b` ← `R1c` (توسيع DECIMAL على SQL Server بتجربة حقيقية) ← **`R-PG` (مرحلة مستقلة)** ← R2..R6.
مكان `R-PG` بعد R1c مقصود: لازم الـschema والأنواع تثبت أولًا، وإلا نترجم مرتين.

### مرحلة R-PG (مؤجّلة، تتخطط تفصيليًا بعد استقرار R1c)
1. محوّل `src/db/postgres.js` (مكتبة `pg`، تحويل `?` ← `$n`، `RETURNING`، `NUMERIC` ← رقم، `Dec`).
2. هجرات `db/postgres/` كتابة يدوية + اختبار schema parity مقابل SQL Server.
3. نفس `scripts/*-precision-check` للـPostgreSQL (أنواع ومقاييس حقيقية).
4. تشغيل Baselines A/B/C وجميع العمليات الطبية والمحاسبية والمخزنية على PostgreSQL، وأي فرق غير مبرَّر = فشل مرحلة.
5. اختبار تزامن (مخزون/عدّادات/أقساط) على المحركين.
6. دليل نقل بيانات منشأة من محرك لمحرك (اختياري، قرار منفصل).
